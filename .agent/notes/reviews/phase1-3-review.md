# Phase 1–3 review — Koan browser UI views controllers

Chromium rev: `158.0.8111.0` @ `67e29b8287f1` (matches `~/work/koan/chromium/src`).
Scope: `src/browser/ui/views/{koan_glance_controller,koan_compact_mode_controller,koan_workspaces,koan_browser_view_controller}.{h,cc}`.

## koan_glance_controller.{h,cc}

- **should-fix — Esc / window.close destroy the overlay widget synchronously while a key/UI event for that widget is still on the stack.**
  `koan_glance_controller.cc:392-408`: `CloseContents()` and `HandleKeyboardEvent()` (Esc) call `Close()` → `DestroyWidget()` (cc:340-346) → `widget_->CloseNow()` + `widget_.reset()`. The Esc key arrives through the renderer input-ack stack: `RenderWidgetHostImpl` → `WebContentsImpl::HandleKeyboardEvent` (`content/browser/web_contents/web_contents_impl.cc:4881-4889` → `delegate_->HandleKeyboardEvent(...)`), i.e. while the `NativeWebKeyboardEvent` is still being processed for the native window *of the overlay widget itself* (the Glance `views::WebView` and its `RenderWidgetHostViewAura` live inside that widget's window: cc:90-92, 246-247). `content::WebContainerDelegate::CloseContents` likewise fires mid-renderer-message (`window.close()` handling). `views::Widget::CloseNow` documents: "This will destroy the window handle … should not be called from any code that expects it to be valid beyond this call" (`ui/views/widget/widget.h:948-954`), and content itself comments on exactly this destroy-during-input hazard at `content/browser/renderer_host/render_widget_host_impl.cc:1916-1927` (`"|this| may already be destroyed"`). The controller's own click authors got this right — `PostAction()` (cc:44-48, 254-258) defers exactly because "they destroy the overlay widget, which must not happen inside one of its own buttons' click handlers" — but the Esc and window.close paths bypass that protocol.
  Failure scenario: Shift+click a link (Glance opens), press Esc. `CloseNow()` tears down the widget, its aura window, the WebView, and detaches the focused RWHV's window *from within* the event dispatch of that window; behaviour after `Close()` returns is undefined (crash in post-dispatch code reaching into the destroyed window/view tree is the expected form). Same stack for JS `window.close()`.
  Fix: make `HandleKeyboardEvent`'s Esc branch and `CloseContents` end with `PostAction(&KoanGlanceController::Close)` (+ `return true`) so the widget teardown happens after the input stack unwinds, matching the button protocol; keep `DestroyWidget()` synchronous only inside `TakeContents()`/`OnBrowserViewDestroying()`, where no event for the widget is live.

- **nit — `OnTabStripModelChanged` (cc:410-418) only reacts to `selection.active_tab_changed()`; the controller never clears `source_`/closes Glance on a `TabStripModelChange::kRemoved`/detached move of the source tab without an activation change.** Intra-window drags can produce remove+selection pairs, so this is currently defensive-by-accident; on any future flow that removes the active tab without an activation change, `source_` (raw_ptr, cc:94) survives the tab. Consider also binding the close to removal of the source's tab. No deref found today (`GetIndexOfWebContents` only compares pointers, `TabStripModel.h:~500`), so keeping severity low.

- **pass — `TakeContents()` (cc:276-281).** Destroying the widget before moving the contents out is safe: `views::WebView::~WebView` does not delete/touch the `WebContents` (`ui/views/controls/webview/webview.cc`, ~WebAura), the controller owns the WebContents via `unique_ptr` (b:93), the delegate is cleared (cc:278), and reattaching the contents to another widget's `NativeViewHost` is the standard `TabDragController` flow (`content` reparenting). `SetWebContents` need not be cleared before `CloseNow`.

- **pass — `InsertWebContentsAt` / `AddToNewSplit` usage (cc:295-321).** Signatures match this rev: `int InsertWebContentsAt(int, std::unique_ptr<WebContents>, int add_types, std::optional<tab_groups::TabGroupId> = nullopt)` (`chrome/browser/ui/tabs/tab_strip_model.h:288-292`), `AddToNewSplit(std::vector<int>, split_tabs::SplitTabVisualData, SplitTabCreatedSource)` (`tab_strip_model.h:666-669`), `SplitTabVisualData(split_tabs::SplitTabLayout)` (`components/split_tabs/split_tab_visual_data.h:28`), `kLinkClick` (`chrome/browser/ui/tabs/split_tab_metrics.h:39`), `ADD_ACTIVE`/`ADD_INHERIT_OPENER` (`tab_enums.h:49,61`). Group handling for a source in a group is correct (insert adjacent + explicit group, both calls).

- **pass — `HandleKeyboardEvent` forwarding (cc:407).** `BrowserView::HandleKeyboardEvent(const input::NativeWebKeyboardEvent&)` exists as that 1-arg overload in this rev (`chrome/browser/ui/views/frame/browser_view.h:611`), matching the call.

- **pass — PostAction weak_ptr discipline (cc:256-258) and the `Close()` deferred `DeleteSoon` for the WebContents (cc:267-269); both safe against controller/WebContents lifetime races.

## koan_compact_mode_controller.{h,cc}

- **nit — `views::MenuController::GetActiveInstance()` is process-global.** `ShouldKeepToolbarRevealed()` (cc:436) suppresses the hide timer whenever a menu is open in *any* window or widget in the process (`MenuController::active_instance_` is a global static, `ui/views/controls/menu/menu_controller.cc:671-674`; upstream's own header says to prefer `GetForOwnerWidget(widget)` — `menu_controller.h:141-143` — because the active instance may even belong to a different widget). With two windows, an open context/app menu in window B freezes the toolbar of window A. Fix: track menus per-widget or use `MenuController::GetForOwnerWidget(browser_view_->GetWidget())` plus a `views::FocusManager`/menu-instance-scoped check.

- **pass — top-container reparent vs `ReparentTopContainerForStart/EndOfImmersive` (`chrome/browser/ui/views/frame/browser_view.cc:3804-3860`).** Koan's Activate/Deactivate (cc:232-241, 341-356) mirror the upstream sequence correctly for this rev: `SetPaintToLayer` + `SetFillsBoundsOpaquely(false)`, overlay lookup, and the `kViewDoesNotLayOutChildren` default-true on `TopContainerView` (`top_container_view.cc:24`) with re-set on restore (cc:238, 355) — including recording/restoring the child index for Z-order (upstream crbug.com/454852658 comment, browser_view.cc:3844-3848). `GetTopContainerOverlayView` (cc:64-75) is valid because the overlay *is* a direct `NonClientView` child (`ui/views/widget/non_client_view.cc:64-74` via `Widget::Init` calling `WidgetDelegate::CreateOverlayView`, `ui/views/widget/widget.cc:608`, `browser_view.cc:4126-4135`).

- **pass — fullscreen interaction.** Compact mode never activates in fullscreen (cc:193 `UseContentCard` → `koan_content_card.cc:14-17` returns false when `IsFullscreen()`), so it cannot race upstream's immersive reparenting from a bad state; `OnBrowserViewLayout` → `UpdateActiveSoon` (cc:133-137, 197-201) defers (De)Activation out of layout via post-task (no reparenting inside a layout pass — matches upstream's `OnImmersiveFullscreenEntered/Exited` doing `DeprecatedLayoutImmediately` afterwards, browser_view.cc:6025-6053).

- **pass — runtime vertical-tabs toggle.** `ShouldBeActive()` re-evaluates `ShouldDrawVerticalTabStrip()` on every layout, and `Deactivate()` restores collapse state and removes hot zones/controls (cc:322-370); `VerticalTabStripStateController::From(browser())` null-guards match the interface (`chrome/browser/ui/tabs/vertical_tab_strip_state_controller.h:54-72`).

- **pass — teardown.** `DestroyFor` runs at the very start of `~BrowserView` (`browser_view.cc:1123-1125`), before child views are nulled and `RemoveAllChildViews()` (browser_view.cc:1136-1175), so the hot zones / window controls / switcher removals and the FocusManager de-registrations (cc:116-121, 149-158) operate on live objects; the widget is still valid at that point (`browser_widget_` nulled only at dtor end, browser_view.cc:1159-1160).

- **pass — `KoanHotZone` bounds (cc:478-488) sit on BrowserView children (BrowserView children later in z-order draw on top, cc:246-260), so the collapsed strip can slide over them.**

## koan_workspaces.{h,cc}

- **should-fix — workspace tint save/restore loses the user's theme (data loss), cross-window and re-entry races.**
  `koan_workspaces.cc:433-479` (`UpdateTint()`). The "original" user colour is snapshotted only once, guarded by the profile pref `prefs::kWorkspaceTintSaved` (cc:446-453):
  (a) While a workspace is active, the user picks a new custom colour from the theme dialog (`ThemeService::SetUserColor`, `chrome/browser/themes/theme_service.h:208`). The snapshot still holds the *pre-workspace* colour, and `kWorkspaceTintSaved` stays true, so the next `ShowAllTabs()` → `UpdateTint()` restore (cc:465-478) silently discards the user's newer choice and reinstates the stale snapshot.
  (b) Two windows (same profile) share `kWorkspaceTintSaved*: Window A focuses workspace W (saves user colour, sets tint). Window B focuses workspace W2: saved already true → does NOT re-save, overwrites tint with W2's seed. Window B exits to "All tabs": restores the *saved* colour (fine), sets saved=false. Window A is still tinted with W's seed; the next time A exits to "All tabs", `UpdateTint()` early-returns (cc:465-467, saved false) → **A's window (and the whole profile theme) stays stuck on the workspace seed colour permanently**; the user must re-customise manually.
  Fix ideas: snapshot the restore colour whenever the *current* `ThemeService::GetUserColor()` differs from all tint seeds (and from the identity currently applied), rather than only once per flag; and key the flag/prefs snapshot to the window (or route restores through a shared owner that includes both windows' focus state).

- **nit — switcher placement relies on class-name string probes.** `InstallSwitcher()` (cc:290-301) finds `"VerticalTabStripRegionView"` then its first `"FlexLayoutView"` child and appends the switcher there. If the region ever gains more than one FlexLayoutView child (e.g. a second flex container around the new-tab pill), the switcher re-attaches to a visually wrong container. Use the metadata class names available after `BEGIN_METADATA` (typed) or a stable element identifier instead of `GetClassName()` string compares.

- **pass — TabStripModelObserver hygiene.** Observer added once and only when `IsEnabled()` (cc:233-235); removed in `OnBrowserViewDestroying` under the same predicate. With a terminal browser, all of `IsEnabled()`/`GetIsNormalType()`/`SupportsTabGroups() == group_model_ != nullptr` (`tab_strip_model.h:714`) hold unchanged at `~BrowserView` start (browser_view.cc:1124-1128, where `browser()` and the model are still alive — the destructor's `CHECK_EQ(0, …count())` right after). If the two evaluations ever diverge, `TabStripModel::~TabStripModel` (`tab_strip_model.cc:289-293`) calls `observer.ModelDestroyed(...)` on a deleted controller — worth a comment or an unconditional `RemoveObserver` in `OnBrowserViewDestroying`.

- **pass — no re-entrancy into TabStripModel from its own notifications.** `adopt_pending_` + post-task (cc:376-390, 396-416), and switcher rebuilds anti-coalesced + post-task with WeakPtr (cc:304-312), keep `AddToNewGroup/AddToExistingGroup`/`EnterFocusMode` out of the observer turn; `PostTask` with `weak_factory_` is cancelled by `DestroyFor`'s `ClearProperty` deletion. `AdoptUngroupedTabs` re-validates focused group/index/group membership postu jump (cc:398-414). `AddToExistingGroup(indices, group, bool add_to_end)` signature matches (`tab_strip_model.h:692-694`).

- **pass — `CreateWorkspace()` (cc:358-370).** `chrome::AddTabAt` (foreground) + `AddToNewGroup({count-1})` + `ChangeTabGroupVisuals` + `EnterFocusMode` — all real APIs in this rev (`tab_strip_model.h:683-686, 729, 758`, `chrome/browser/ui/browser_tabstrip.h:45`); the transient adopt task that fires between operations re-checks and no-ops on the already-grouped tab (cc:411-414).

- **pass — accelerator/button lifetimes.** Buttons bind `base::Unretained(controller)` (cc:189-214); the buttons are deleted together with the switcher view (cc:275-277) and never fire after controller destruction (callbacks run on the same UI sequence; controller destroyed strictly before the switcher view's destructor runs).

## koan_browser_view_controller.{h,cc}

- **pass — ownership and lifecycle.** Owned via `DEFINE_OWNED_UI_CLASS_PROPERTY_KEY` (cc:26-27, 54-56) so the controller dies exactly where upstream's `~BrowserView` expects (first line, `browser_view.cc:1123-1126`); `DestroyFor` performs the per-child `OnBrowserViewDestroying` *before* `ClearProperty` deletes the controller (cc:60-67), so every one of the teardown hooks runs with `top_container_`/`infobar_container_`/`multi_contents_view_` still live (upstream nulls them only at dtor end, browser_view.cc:1156-1175).

- **nit — `OnViewBoundsChanged` (cc:89-96) pipes every `multi_contents_view` bounds notification into `compact_mode_->OnBrowserViewLayout()` + `glance_->OnBrowserViewLayout()`, including the many inner-child bounds events and even (via the `browser_view` observation) window moves; each one runs `ShouldBeActive()` (prefs + feature + string probes) — cheap but redundant, and a renamerelease of `IsCompactModeActive(browser_view)`. Consider observing only bounds changes on the browser view (contents area bounds derive from it) or coalescing, as done for `UpdateSwitcher`.

- **pass — `KoanBrowserViewController::Create`/`CreateFor`'s `CHECK(!From(browser_view))` prevents double creation (cc:53), and the static hook wiring (`browser_view.cc:1121`/`1125` → `koan_browser_view_hooks.cc:11-17`) guarantees exactly one instance per BrowserView for all other controllers to find via `From`.

- **pass — `UpdateContentCard` (cc:98-108) uses the same `GetActiveContentsContainerView()/SetRoundedCorners()/GetBackgroundRadii()` APIs (`multi_contents_view.h:78,94`, `contents_container_view.h:142`) and skips split view, matching the upstream hooks' radii updates.

## Verdict
No blocker-level crash/export faults found; the widget destruction vs event-dispatch ordering in Glance and the workspace tint state machine are the two designs most likely to bite (one undefined-behaviour risk, one real user-data loss). Renderer/view API use matches revision 158 throughout (verified signatures cited per finding). Fix the two should-fix items before the TouchController coverage pass; everything else is safe to layer subsequent phases onto.
