# Updating Koan to a new Chromium

Chromium ships a milestone every 4 weeks. Koan stays small on purpose so that
moving to a new revision is mechanical:

- All Koan code lives in `src/` (seen by GN as `//koan`).
- Upstream files carry one-to-a-few-line **hook patches**, one file per
  patched upstream file in `patches/`. Each calls into `//koan`, except the
  freezing exemptions in `components/performance_manager` (a `component()`
  shared library, which can't depend on `//koan`), which carry their logic in
  the patch; see the table. A static library linked only into `chrome`, such
  as `components/omnibox/browser`, may call into `//koan` through a
  header-only hooks target; the definition lives in `//koan/browser/ui/views:impl`,
  so a binary that links the library without `//chrome/browser` (e.g.
  `components_unittests`) wouldn't link.
- Bulk branding (product name strings, `BRANDING`, logos) is applied by
  `scripts/apply_branding.sh` rather than stored as patches.
- Upstream feature defaults Koan relies on are set in one place,
  `src/browser/koan_feature_overrides.cc`.

## Following Chromium releases

Koan is a daily-driver browser, so it takes Chrome's security fixes, which
ship in Stable point releases about weekly. A trunk snapshot gets none of
them. So the pin is always a **release tag of the milestone we're on**,
never a main commit:

- `CHROMIUM_VERSION` line 1 is the tag (`158.0.8127.2`), line 2 the commit
  it points to. `scripts/bootstrap.sh` (Linux, the Mac CI and a local Mac
  alike) checks out exactly that commit; `scripts/ci/check_patches.sh`
  checks the patches against it.
- A milestone's tags are on its **release branch**, `refs/branch-heads/<BUILD>`
  (158.0.8127.x is `branch-heads/8127`), not on main. Fetch a tag by name:
  `git fetch --depth=1 origin refs/tags/158.0.8127.2`. A branch-head moves
  past its last tag (it collects fixes before they are tagged); don't pin it.
- Where Chromium is: [chromiumdash](https://chromiumdash.appspot.com/releases?platform=Mac)
  lists the Mac channels; the API behind it,
  `https://chromiumdash.appspot.com/fetch_releases?channel=Stable&platform=Mac&num=5`
  (also `Beta`), is what the watcher below reads.

| What happens | Do | Within |
|---|---|---|
| Our milestone gets a **point release** (`158.0.8127.x` -> `158.0.81xx.y`), Beta or Stable | bump the pin ("Point release" below) | a few days |
| A **newer milestone reaches Stable** | rebase onto it ("New milestone" below) | about 2 weeks of it reaching Stable |
| A newer milestone is only Beta or Dev | nothing | |

Until we take a new milestone we stay on our milestone's latest Stable point
release. A Beta of our own milestone is fine as the pin until the milestone
is promoted: its tags are the Stable ones.

### The watcher

`.github/workflows/chromium-releases.yml` (ubuntu, every 6 hours, `contents:
read` and `issues: write` only) polls chromiumdash for Mac Beta and Stable
(`scripts/ci/chromium_releases.py`). When our milestone has a newer point
release, or a newer milestone is at Stable, it runs
`scripts/ci/check_patches.sh` against that version and opens or updates the
one issue labelled `chromium-update`: versions, release dates, the date each
is due, and which patches fail. It closes the issue when the pin has caught
up, and says nothing while nothing changed. Run it by hand from the Actions
tab ("Run workflow", with *dry run* to only print), or locally with
`python3 scripts/ci/chromium_releases.py --dry-run`.

The same run keeps an early warning, report only: the newest Beta of the first
milestone that is neither ours nor at Stable yet is checked the same way, and
ONE other issue, labelled `chromium-next-beta`, says whether the patches still
apply (title "M159 Beta early warning: 159.0.8200.5, 1 of 114 patches fail").
It has no due date and asks for no pin change. It stays open: when M159
reaches Stable the issue is retitled to the next milestone's Beta (M160), and
it closes only when no later Beta exists. A comment is posted only when the
set of failing patches changes. See "Rehearsing the next milestone".

### Point release

Rarely touches the hooks.

```sh
scripts/ci/check_patches.sh 158.0.8140.5     # no checkout needed; what the issue shows
```

1. If every patch is `ok`: change `CHROMIUM_VERSION` to the new tag and its
   commit (`scripts/update_chromium.sh` writes it; or
   `git ls-remote https://chromium.googlesource.com/chromium/src refs/tags/158.0.8140.5`)
   and open a PR. CI checks the patches against it.
2. A `CONFLICT` or `MISSING` (upstream moved or renamed the file): port the
   hook on the PR's branch, as for a new milestone below.
3. Switch the checkout you build in: `scripts/update_chromium.sh 158.0.8140.5`.
   A point release changes few files, but a toolchain roll (`CLANG_REVISION` in
   `tools/clang/scripts/update.py`) rebuilds everything: look first. On
   macOS, the nightly build CI (#69, `macos.yml`, once PR #70 is merged)
   builds whatever `CHROMIUM_VERSION` pins, so it follows on its own; a local
   Mac build runs `scripts/update_chromium.sh` too.

### New milestone

As above, and a milestone rebases more:

1. `scripts/ci/check_patches.sh <tag>`, then port every conflict on a branch
   (below). Open PRs that touch hook patches need the same port: list them
   with `gh pr diff <n> --name-only | grep ^patches/` and check those patch
   files against the tag.
2. Upstream renames code and enums between milestones (M158 split the tab
   layouts into `*_vertical_layout.cc` files and renamed
   `WindowOpenDisposition::NEW_FOREGROUND_TAB` to `kNewForegroundTab`):
   patches that apply can still fail to compile. `grep` `src/` and the `+`
   lines of the patches for what the build breaks on.
3. `scripts/update_chromium.sh <tag>`, build, and the audit and smoke tests
   below.
4. Update the tables and prose here that name moved files.

### Rehearsing the next milestone

A new milestone's Beta comes about 4 weeks before it is Stable. Rehearse it
then, so that when it reaches Stable the 2-week window is a pin bump and not a
port. The rehearsal never moves the pin on `develop`, and never merges its
ports early: they target the new milestone and don't apply to the pin.

1. **Start.** The watcher opens an issue labelled `chromium-next-beta`
   ("M159 Beta early warning: ...") with the patch check against the newest
   Beta of the next milestone. Run it yourself any time:
   `scripts/ci/check_patches.sh 159.0.8200.5`. No conflicts is good news, not
   the end: go on to 3.
2. **Patches.** Branch `rehearsal/m159` from `develop`. Port every `CONFLICT`
   and `MISSING` on it (see "Procedure"), keeping each patch a call into
   `//koan` (rules in `.agent/notes/agent-brief.md`, "Upgrade-safe code").
   Open PRs that add patches need the same port (list them with
   `gh pr diff <n> --name-only | grep ^patches/`). `python3
   scripts/ci/patch_report.py --base origin/develop` shows what the ports cost.
   Rebase the branch on `develop` weekly, and re-run the check when the Beta
   changes (the issue updates itself).
3. **Compile.** On the branch set **both lines** of `CHROMIUM_VERSION`: the
   Beta's tag, then the commit it points to (`check_patches.sh` stops if they
   disagree; `scripts/update_chromium.sh <tag>` writes both, but it moves the
   checkout under its own `$ROOT/chromium/src`). So use a **second Koan
   clone with its own `chromium/`** (the daily clone keeps its objects; a new
   milestone changes the compiler and rebuilds everything, plan for an
   overnight build). Build there through the Mac loop, the first
   time with `autoninja -C out/Koan -k 0 chrome` (`scripts/build.sh` has no
   pass-through) so one pass lists every compile error. For M158 that found
   one failing step in about 58,000: `PopupBlockerTabHelper` had become a
   per-tab helper. Fix `src/` on the branch: same code on every milestone
   (rule 5), so an API rename is fixed at rebase time, not behind an `#if`.
4. **Regression.** Run the Mac checks against the new build and against the
   pin's build, and compare: the `scripts/mac` drivers (`vtabs.sh` modes) and
   `steps/*.md`, and every guard in
   `.agent/notes/upstream/behaviour-guards.md` that is runnable. A guard that
   fails is an upstream behaviour that changed: fix the hook, or update the
   guard and the REBASE row. Rows with no guard ("none") are where a break is
   silent: look at those by hand.
5. **Record.** Write `.agent/notes/upstream/rehearsal-m159.md`: the patch
   table, the compile errors and their fixes, the guards that failed, the
   hours spent. When the milestone reaches Stable and the `chromium-update`
   issue opens, rebase the branch on `develop`, set the Stable tag (a point
   release of the same branch: re-run the patch check and the build), open the
   PR, and delete the branch.

What the rehearsal does not touch: the pin and the patches on `develop`, and
the daily Chromium checkout.

### Keeping the next rebase mechanical

The rules every change follows are in `.agent/notes/agent-brief.md`
("Upgrade-safe code"). What enforces and measures them:

- `scripts/ci/patch_report.py` runs on every PR (job "Patch health"): the
  patch count, changed upstream lines, new and grown patches, and it fails a
  new patch without a row in the hook table below.
- Every row names the upstream **behaviour** the hook assumes, and
  `.agent/notes/upstream/behaviour-guards.md` says which test fails when it
  changes (and which rows have none).
- `.agent/notes/upstream/patch-audit.md` lists what the current patches get
  wrong against the rules, with a fix for each; work through it when a file is
  open anyway.

## Procedure

```sh
scripts/ci/check_patches.sh 159.0.8150.0    # will today's patches apply? (no checkout)
scripts/update_chromium.sh --check          # ... to the checkout's HEAD
scripts/update_chromium.sh 159.0.8150.0     # un-brand, un-patch, fetch the tag, sync, re-apply
scripts/build.sh                            # most of the tree rebuilds
```

`update_chromium.sh` takes a release tag (not a commit or branch), checks the
patches against it before changing anything, and stops if one conflicts. It un-patches by putting back every file any
Koan patch set touched (this branch's, which may be newer than what is applied,
and the list in `$KOAN_PATCHED_FILES`, default `.cache/patched-files`), and
stops if anything else is modified.
Port that hook on a branch first: get the new file
(`curl -s 'https://chromium.googlesource.com/chromium/src/+/<tag>/<path>?format=TEXT' | base64 -d`
for a checkout-less port, or the file in `chromium/src` after the checkout),
make the same small change, and write `patches/<path>.patch`
(`scripts/apply_patches.sh export` from a checkout); renamed upstream files
get a renamed patch. Then `scripts/apply_branding.sh`.

## Shared hooks for Koan features

Several features need the same upstream places. Each is one hook, and
features plug into it in `src/` rather than patching upstream again:

- **Tab context menu**: `src/browser/ui/views/koan_tab_menu.h`. One hook at
  the end of `TabMenuModel::Build()` (`koan::AddKoanTabMenuItems`, with a
  `koan_submenus_` member in `TabMenuModel` that owns features' submenus) and
  one in each of `TabStripModel::IsContextMenuCommandEnabled()` /
  `ExecuteContextMenuCommand()`. A feature adds a `TabMenuFeature` (add its
  items, enabled state, run a command) to `kFeatures` in `koan_tab_menu.cc`
  and gets its own range of 100 command ids (`TabMenuFeatureId`: split view
  3000, pinned tabs 3100, Spaces 3200, folders 3300). Items are found by
  command id, never by position. `TabMenuContext::AddSubmenu()` gives a
  submenu whose items run like the menu's.
- **Session data, per tab and per window**:
  `src/browser/ui/views/koan_session_data.h`. A feature keeps its data under
  its own key ("koan.<feature>"), as Chromium's session extra data:
  - Per tab: `koan::SetTabSessionData(contents, key, data)` /
    `GetTabSessionData(contents, key)`. It comes back after a restart, when
    a closed tab or window is reopened and when a discard replaces the tab's
    WebContents, and follows the tab, not its index (e.g. folder
    membership).
  - Per window: `koan::SetWindowSessionData(browser, key, data)` /
    `GetWindowSessionData(browser, key)`, for state of the window rather
    than a tab (e.g. folders themselves: names, collapsed, empty ones). It
    comes back after a restart and when a closed window is reopened. Kept on
    `KoanBrowserViewController`, so only windows with Koan's UI have it.

  The store keeps a copy: call `Set...()` after every change. A feature that
  acts while a tab or window is restored adds a `TabRestoreHook` (it may
  replace the tab's pages) or `WindowRestoreHook` (the window exists, its
  tabs don't yet) to `kTabRestoreHooks` / `kWindowRestoreHooks` in
  `koan_session_data.cc`. The hooks: `SessionServiceBase::BuildCommandsForTab`
  and `BuildCommandsForBrowser` (the session file's rebuild drops extra data
  otherwise), `CreateRestoredTab` in `browser_tabrestore.cc`,
  `SessionRestoreImpl` in `session_restore.cc` (`CreateRestoredBrowser`, and
  where the first window is restored into the open browser), and
  `BrowserLiveTabContext::GetExtraDataForTab`, `GetExtraDataForWindow` and
  `Create` in `browser_live_tab_context.cc`.
- **"Is this tab pinned?"**: `koan::IsPinnedForUser(tab)` in
  `src/browser/ui/views/koan_pinned.h`: an Essential (Chromium's
  pinned tab) or a tab pinned to its Space, which Chromium doesn't know as
  pinned. Upstream's Close Other Tabs, Close Tabs Below and back-to-opener,
  and Koan's Clear, ask it; any feature that leaves pinned tabs alone (moving
  tabs between Spaces or into folders) should too. The freezing and Memory
  Saver exemptions get these tabs through the page's pinned state, which
  Koan sets for them.

Features that adopt these (Spaces, folders) drop their own copies of the
same files: `koan_tab_menu.{h,cc}`, `koan_session_data.{h,cc}`, and the
`tab_menu_model.{h,cc}`, `tab_strip_model.cc`, `sessions/BUILD.gn` and
`session_service_base.cc` patches, adding their entries in `src/` instead.
Their menu ids move into their `TabMenuFeatureId` range (e.g. folders' "Move
to Folder" from 3002, inside split view's range, to 3300+).

## Agent control: the method policy

Agent control (`.agent/notes/agent-control.md`, issue #180) lets a local agent drive tabs over a filtered DevTools
protocol. What it may call is a per-method table, **unlisted = deny**, in `src/browser/agent/koan_agent_policy.cc`, with a
`ParamFilter` column naming the parameter filter a forwarded method needs. A roll must not make anything reachable by
inheriting it, so the check below fails on any change to what an agent can reach:

```sh
scripts/ci/check_agent_policy.sh [version]        # fetches the PDL files of a revision (the pin by default)
scripts/agent/check_policy_coverage.py            # against chromium/src, or --chromium-src DIR
scripts/agent/check_policy_coverage.py --list     # kDeny rows for the new methods of listed domains
scripts/agent/check_policy_coverage.py --update-baseline   # after a review
```

It runs in CI against `CHROMIUM_VERSION`, and `scripts/update_chromium.sh` runs it against the new tag before it
touches the checkout. It fails when:

- a domain is neither fully listed nor in the denied domains, a listed domain has a method without a rule (new methods
  start as `kDeny`; allowing one is a review decision), or a rule names a method that no longer exists;
- the **parameters or results of a forwarded method** changed (`scripts/agent/policy_baseline.json` holds a schema hash
  of each; comments in the PDL do not count). A new parameter on `Page.createIsolatedWorld` (like
  `grantUniveralAccess`) or `Input.dispatchKeyEvent` (like `commands`) is exactly what this catches: decide whether the
  method's `ParamFilter` covers it;
- a listed domain gained or lost an **event** (a new `Network` event could carry cookies: the event allowlist and the
  scrubber decide);
- the **schema of an allowlisted event, or of a type it reaches**, changed (the baseline holds one hash per event over the
  event and every type it refers to, and the list of fields left in the Network events after the scrubber); or an event
  delivered unscrubbed reaches a field named like a secret, a header map or an execution context;
- an event in the **event allowlist** (`src/browser/agent/koan_agent_events.cc`) no longer exists, is unsorted, is in a denied
  domain, or a Network event is not marked for the scrubber (the allowlist is explicit: an event that is not listed is dropped,
  so a new event is never delivered until it is added on purpose);
- a row between the markers did not parse.

Things the policy relies on upstream doing, which the code cannot check and a roll can change; re-read them in the new
source when the gate fires or the milestone moves: `Network.enable`'s `maxPostDataSize` unset means bodies are not inlined
into `requestWillBeSent`; the DevTools protocol dispatcher ignores unknown parameters and matches names case-sensitively
(so `Commands` is not `commands`); `Input.dispatchKeyEvent`'s `commands` is the only route from a key event to the clipboard
(Blink's editing behaviour has no Copy/Paste key entries); `Page.captureScreenshot` sizes its bitmap from `clip`, and from
the whole page (up to 128K a side) with `captureBeyondViewport`; `Page.createIsolatedWorld`'s `grantUniveralAccess` is the
only way a world gets universal access; a header map is always an object named `*headers` and raw header text is always
`*headersText`, and `Runtime.enable` reports every world of a tab's frames, extension content-script worlds included.

The gateway (`src/browser/agent/koan_agent_gateway.*`, `koan_agent_socket.*`, `koan_agent_peer.*`) adds no patch but relies on
upstream behaviour that the code cannot check; re-read these when `net/` or the Security-facing code moves:
`net::UnixDomainServerSocket::AcceptSocketDescriptor` accepts the next connection by itself when its auth callback says
no (`AuthenticateAndGetStreamSocket`, a refused peer never reaches the gateway; `GatewayOptions::kernel_uid_for_testing`
has a test for it), hands back a descriptor whose close-on-exec state is not relied on (the gateway sets it), and reports running out of
descriptors as `ERR_INSUFFICIENT_RESOURCES` (the accept loop backs off for a second only on that);
`net::SocketPosix::AdoptConnectedSocket` makes the descriptor non-blocking, `ReadIfReady` returns 0 at end of stream
and `Close()` cancels a pending read or write; `getsockopt(LOCAL_PEERTOKEN)` is the connector's audit token, fixed at
connect time; `SecCodeCopyGuestWithAttributes` with an audit token finds nothing once the process has exec'd or the pid
was reused; `kSecCSBasicValidateOnly` skips the resources of a bundle; `proc_pidinfo(PROC_PIDTBSDINFO)` has a start
time (`pbi_start_tvsec`, `pbi_start_tvusec`) and a parent pid (`pbi_ppid`) in public headers, and `proc_pidpath` follows an exec; `confstr(_CS_DARWIN_USER_TEMP_DIR)` is a
0700 per-user directory. The traffic annotation `koan_agent_gateway` is defined in the gateway; Koan does not run
Chromium's annotation auditor, so a change to the fields `net::DefineNetworkTrafficAnnotation` requires shows up as a
compile error, not as a failed audit; re-check it then.

The wiring (`src/browser/agent/koan_agent_service.cc`, `koan_agent_approval_dialog.cc`, the indicator in
`src/browser/ui/views/koan_agent_indicator.cc`) adds no patch either: the first `KoanBrowserViewController` creates the
service. It uses upstream symbols, so a rename breaks the compile: `prefs::kDevToolsRemoteDebuggingAllowed` (local state;
policy `RemoteDebuggingAllowed=false` keeps the gateway off, T-ready-5), `browser_shutdown::AddAppTerminatingCallback`,
`GetLastActiveBrowserWindowInterfaceWithAnyProfile`, `chrome::ShowBrowserModal`, `content::GetIOThreadTaskRunner` (the
gateway needs a `MessagePumpForIO` thread, which the browser IO thread is). Behaviour it relies on: `chrome::DIR_USER_DATA`
is set before local state is registered (the Agent ready default is computed then, T-ready-3); a browser-modal dialog's
close callback runs for Esc and for closing the window (both deny, T-ready-4).

The keep-alive lease (`src/browser/agent/koan_agent_lease.*`) adds no patch: `WebContents::IncrementCapturerCount` (visible,
no wake lock), `WebContents::ForbidExternalPopupMenus` (macOS, `USE_EXTERNAL_POPUP_MENU`), `PageLiveStateDecorator::SetIsPinnedTab`
and `SetGlicActuationState(kActuatingOnBackgroundTab)`. Behaviour it relies on: the pinned bit exempts a page from Koan's
freezing and from Memory Saver's discard, and nothing outside performance_manager reads it as "the user pinned it"
(T-keep-5, T-keep-6, T-keep-12; `koan_pinned_tabs.cc` composes it with the user's pin); the actuation vote is gated by
`kGlicActuationPriorityVoter`, on by default (T-keep-8); a visible capturer keeps rAF, CSS animations and unthrottled timers
on a hidden tab (T-keep-1..4); macOS's Low Power Mode is read from `NSProcessInfo.lowPowerModeEnabled`, since Chromium has no
wrapper for it.

A review that changes the outcome updates the table and the baseline in one change. The other things to re-check on a roll
(the untrusted-client domain list, the `DevToolsAgentHostClient` flag defaults, the `PageLiveStateDecorator` setters the
keep-alive uses) are in the design's section 14 and become REBASE rows with the PRs that add them.

## After every rebase, re-audit the hooks

`update_chromium.sh` prints every `koan::` call site in `chromium/src`.
For each, check the surrounding upstream code still means what the hook
assumes. A new patch needs a row here (CI fails without one): what it hooks,
why no extension point fits, and the upstream **behaviour** it assumes, with
the test that fails if that changes (see
`.agent/notes/upstream/behaviour-guards.md` for the existing ones):

| Hook | File | Assumption to re-check |
